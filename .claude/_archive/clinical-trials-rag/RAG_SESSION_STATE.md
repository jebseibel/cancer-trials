## What the real data taught us (n=50, measured, not assumed)

The hand-built fixture in `:datafetcher` is misleading — **a parser written against it
matches nothing in production**:

| Shape | Frequency |
| --- | --- |
| Escaped markdown (`\*`, `\<`) survives ingestion | 23/50 |
| Bullet markers | `*` 632 lines, numbered 163, **hyphen 0** |
| Both inclusion + exclusion headers | 48/50 |
| No headers at all (legacy `DISEASE CHARACTERISTICS:` format) | 2/50 |
| Nested/indented sub-bullets | 12/50 |
| Prose, no bullets | 5/50 |
| Criteria length | min 95, median 1,046, **max 13,771** chars |

Also: the longest trial writes `Inclusion Criteria` with **no colon**.

That 13,771 max matters — the local model's window is ~256 word pieces (~1,000 chars), so
the biggest block is ~14x the window. Per-criterion chunking is what keeps it searchable
instead of silently truncated.

## Resolved: parent suppression (was the blocking question)

**Decided: suppress parents that have children.** A bullet followed by a more-deeply-indented
bullet is *structure*, not a criterion — it is about to be prefixed onto its children, so
emitting it alone adds a chunk that answers nothing. `Absolute neutrophil count (ANC)` was
the canonical case: alone it names a lab value with no threshold, i.e. the one chunk that
cannot answer "what neutrophil count do I need?".

Implemented structurally (a following deeper-indented bullet marks the pending one as a
parent), not via the earlier colon heuristic — `ANC` has no colon but is still structure.
Verified output:

```
[INCLUSION #7] Absolute neutrophil count (ANC) For monotherapy and pembrolizumab
               combination therapy cohorts: >= 1000/uL
[INCLUSION #8] Absolute neutrophil count (ANC) For PLD combination therapy cohort: >= 1500/uL
```

Both keep the lab name (so "neutrophil count" still retrieves) and both carry a threshold
(so they can answer). The bare parent is gone.

The test that surfaced this was also wrong and was replaced: "one chunk is a prefix of
another" is a symptom, not the rule — siblings *should* share a parent prefix. It now asserts
no chunk is **fully contained** in another.

## Four defects found and fixed (don't re-introduce)

Found by *inspecting real output*, not by tests — the original assertions were structural
(`length >= 3`) and passed happily on bad chunks. Regression tests now cover all three.

1. **Labels prefixed onto everything** — `"All 3 parts of Study:"` was glued onto all 42
   chunks of a trial, giving them a shared leading phrase that pulls embeddings together
   and blurs the distinctions retrieval depends on. Fixed via `SECTION_LABEL`.
2. **Orphan labels emitted alone** — wasted embeddings, noise in results. Now suppressed.
3. **Near-duplicate siblings** — long parents (500+ chars) were prefixed whole, making
   siblings ~90% identical. Fixed with `abbreviateParent()` (`MAX_PARENT_PREFIX_LENGTH`
   = 160, cutting at the first sentence/clause boundary).
4. **Parents emitted alongside their children** — see "Resolved" above. Chunk count on the
   longest trial fell 69 → 66 → 60 across the three rounds of fixes.

**Every one of these was found by reading real output, not by a passing test.** The original
assertions were structural (`length >= 3`) and passed happily on useless chunks. Keep
`ChunkOutputInspection` until retrieval is proven.

## Qdrant point ids must be UUIDs (cost two restarts)

The first backfill run failed on **all 50 trials** with
`IllegalArgumentException: UUID string too large`. Qdrant point ids must be a UUID or an
unsigned integer; `TrialChunk.id()` was returning the readable `extid:SOURCE:ordinal` key.

Fixed by hashing that key through `UUID.nameUUIDFromBytes()` — content-addressed, so the same
chunk always maps to the same id, preserving the idempotency that delete-then-insert relies
on. The readable key is now also stored in metadata as `naturalKey`, because a hashed UUID is
opaque when inspecting the store.

Regression test: `TrialChunkerTest.chunkIdsAreValidUuids`.

## Ingestion and indexing are two deliberate steps

`POST /api/ingestion/clinicaltrials` writes to MySQL. `POST /api/rag/backfill` makes it
searchable. **Ingesting does not update the vector store** — search returns nothing for newly
ingested trials until backfill runs.

A combined endpoint was discussed and **deliberately not built** (2026-08-07). Reason: the two
steps have very different costs and failure modes — staging ~1,000 trials is quick, embedding
them is ~26,000 local ONNX inferences — and keeping them separate keeps that visible rather
than hiding it behind one call. Revisit if the manual second step becomes annoying; the cheapest
version is a `?backfill=true` param on the existing endpoint rather than a third endpoint.

The permanent fix for the coupling is candidate #2 below (the after-commit event hook), which
makes new ingestions index themselves.

## Ingestion defaults are configurable (2026-08-07)

`cancer.ingestion.clinicaltrials.*` in application.yml, overridable per request from the

- **`filter.overallStatus` had to be built** — the client was not sending that param at all.
- **Bug fixed:** the controller previously passed `maxStudies` as the *normalization* limit.

## TODO — normalization is the ingestion bottleneck (measured 2026-08-07)

Ingestion speed is dominated by normalization, not by fetching. Measured on a real run of 736
staging rows:

| Phase | Time | Share |
| --- | --- | --- |
| Fetch (1 page of 100 studies) | ~1.1s | **0.4%** |
| Staging (34 inserts) | ~0.7s | 0.3% |
| **Normalization (736 trials)** | **~257s** | **99.3%** |

**349ms per trial**, at roughly **38 database round trips each** (~9.2ms per call). Extrapolated:
1,000 trials ≈ 6 min, 2,456 ≈ 14 min, **18,773 ≈ 110 min**.

Where the 38 round trips go, per trial (counted from 100 real CT.gov payloads):

| Work | Count |
| --- | --- |
| Child INSERTs, one at a time (13.6 locations, 7.2 outcomes, 2.1 interventions, 1.9 arm groups, 0.7 officials) | **~25** |
| `findByName` for conditions + sponsors | ~3.9 |
| `findById` TrialSource, `findByNctId`, create/update, staging update | 4 |
| `findByTrialId` × 5 on re-normalization, plus a delete per existing child | 5+ |

### Already done

- **`NormalizationCache`** (`datafetcher/.../normalization/NormalizationCache.java`) — per-run
  cache for `TrialSource` (was re-fetched once per row for the same row) and condition/sponsor
  `findByName`. Caches negative results too. Logs `cacheHits`/`cacheMisses` on completion.
- **Logging turned down** — `com.seibel.cancer.database.db.service: WARN`. Every DbService
  create/update logged at INFO, so the 736-trial run emitted ~18,400 lines of noise.

Together these remove ~4 of ~38 round trips plus the logging overhead — expect 15-25%, not more.

### NOT done — the big win, and why

**Batching the ~25 child INSERTs is blocked by the schema.** `BaseDb` uses
`@GeneratedValue(strategy = GenerationType.IDENTITY)`, which **disables Hibernate JDBC batching
entirely** — Hibernate needs the auto-increment id back for each row, so `saveAll()` still issues
25 individual round trips. No amount of `spring.jpa.properties.hibernate.jdbc.batch_size` changes
that.

Two ways forward, both needing a decision that is the user's:

1. **Change the id generation strategy** on `BaseDb` (sequence or table generator) so batching
   works. Biggest payoff, but it is a schema-wide change affecting every entity — and DB schema is
   the user's to manage, never touched without an explicit ask.
2. **Native bulk-insert queries** in the child repositories, bypassing Hibernate's entity
   lifecycle. No schema change, but more code, and it sidesteps `BaseDb`'s extid/timestamp/active
   handling — so each one needs to set those explicitly or the rows come out inconsistent with
   the rest of the system.

Also cheap and unblocked: **bulk `deleteByTrialId`** instead of `findByTrialId` then a delete per
child, which would cut the re-normalization path considerably.

### Related: raising the CT.gov page size is NOT a speed fix

`pageSize` max is **1000** (verified: 1001 silently clamps to 1000). Our client uses 100. Measured
fetch times: 100 → 1.06s, 500 → 4.34s, 1000 → 8.16s — so it scales with study count, not request
count, and 100 → 1000 saves only ~20% of a phase that is 0.4% of total runtime (~0.2s out of 259).

Worth raising eventually for a *different* reason: `ClinicalTrialsGovClient` accumulates every
study in a `List<JsonNode>` before staging any of them, so an 18,773-trial pull holds ~280MB of
parsed JSON in heap at once. The fix there is streaming (stage each page as it arrives), not a
bigger page.

### A 110-minute request will not survive HTTP

At the measured rate, a full pull exceeds any reasonable request timeout. The async-job endpoint
noted as out of scope in `FRONTEND_JOB_TRIGGER_PLAN.md` becomes **necessary** at that scale, not
just a nicety.

| recruiting trials I could join now | **0.526** | `Concomitant participation in other clinical trials` | Colloquial phrasing; latched onto "join" as *consent*. Arguably user-education: recruiting status is a metadata **filter**, not a semantic query. |

**Verdict:** good enough to build on. Whether the upgrade is worth it depends on what your real
queries look like — if they use clinical terminology, MiniLM is fine. Do not upgrade on
principle; upgrade if the eval numbers justify it.

**Also observed: a corpus problem, not a model problem.** Nearly every high-scoring hit is
COMPLETED / TERMINATED / UNKNOWN — few of the 50 trials are actively recruiting. For a
discovery tool that is the wrong corpus. Consider passing CT.gov's `filter.overallStatus`
at **ingestion** time, not just filtering at query time. Cheap fix, possibly high value.

## Embedding-model upgrade — attempted, reverted, findings kept

Tried `BAAI/bge-base-en-v1.5` (768 dims). **Reverted deliberately** rather than left broken.
Full technical findings are in `RAG_PLAN.md` §12; the short version:

- ONNX exports live at `onnx/model.onnx`, **not** the repo root (root 404s). Verified 200 for
  BGE-base, E5-base, all-mpnet-base-v2.
- **It OOMs.** Spring AI reads a *remote* model fully into a `byte[]` before caching
  (~440MB contiguous heap). `org.gradle.jvmargs` does **not** cover this — that sizes the
  Gradle daemon, not the forked test JVM.
- **The fix is a `file:` URI, not a bigger heap.** The in-memory read only happens for remote
  resources. `../../../rag/src/test/resources/eval/precache-model.sh` downloads the model and prints the
  URIs to set. This also means the backend needs no raised `-Xmx`.
- Prefer BGE over E5: E5 wants `query:` / `passage:` prefixes that Spring AI does not add, and
  omitting them degrades results silently.

`maxHeapSize = '4g'` in `../../../rag/build.gradle` was **kept** after the revert — the default forked
test heap was too small regardless.

## Tunable config — `cancer.rag.*` in application.yml

Six values that were hardcoded Java constants are now configurable:

```yaml
cancer:
  rag:
    chunking:
      max-parent-prefix-length: 160
      min-criterion-length: 3
      max-prose-chunk-chars: 900     # raise for a model with a longer window
    retrieval:
      chunk-fetch-multiplier: 6
      default-similarity-threshold: 0.0
    backfill:
      page-size: 25
```

Three things to know:

- **Chunking values are not hot.** They only affect chunks as they are *created*, so changing
  one requires a re-backfill before it affects search results. Warned in the YAML comments too.
- **The chunkers still have no Spring dependency.** `RagConfig` builds them as beans from
  configured values via constructors; both keep a no-arg constructor with defaults, so the 21
  chunking tests construct them directly and stay fast.
- **`similarityThreshold` and `pageSize` are boxed (`Double`/`Integer`) on the controller.**
  Omitting them falls back to config. A primitive with `defaultValue` would have made the YAML
  setting permanently unreachable.

## Still open (from RAG_PLAN.md §8, §12)
